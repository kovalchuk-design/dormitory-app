# Гуртожиток (dormitory-app)

Веб-застосунок для шкільного гуртожитку (≈250 учнів, 9–11 класи, поверхи 2–5). Вихователів четверо, вони чергують позмінно (1 день через 3) і на зміні відповідають за **всі** поверхи — поверх не є межею доступу. Інтерфейс — українською.

Стек: Vite + React + TypeScript, react-router (HashRouter), Supabase (авторизація та база даних), vitest. Це статичний сайт, що розгортається на GitHub Pages.

## Ролі

| Роль             | Опис                                              |
| ---------------- | ------------------------------------------------- |
| `admin`          | Адміністратор, бачить усі розділи, зокрема «Адміністрування» |
| `educator`       | Вихователь (бачить і редагує будь-якого учня)      |
| `staff_readonly` | Працівник з доступом лише для перегляду           |

Після входу застосунок завантажує рядок користувача з таблиці `profiles`. Якщо профілю немає, користувач бачить повідомлення «Ваш обліковий запис ще не активовано адміністратором».

## Запуск локально

Потрібен Node.js 20+ (рекомендовано 22).

```bash
npm install
cp .env.example .env.local   # значення Supabase (публічні)
npm run dev
```

Сайт відкриється на `http://localhost:5173/dormitory-app/`.

## Збірка, перевірки, тести

```bash
npm run build   # перевірка типів + production-збірка у dist/
npm run lint    # ESLint
npm test        # vitest (логіка diff/CSV/фільтрів/телефонів/токенів, меню)
```

## Змінні оточення

| Змінна                          | Опис                                  |
| ------------------------------- | ------------------------------------- |
| `VITE_SUPABASE_URL`             | URL проєкту Supabase                  |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публічний (publishable) ключ Supabase |

Ці значення публічні, тому `.env.production` закомічено. **Ніколи** не додавайте в репозиторій `service_role` ключ — безпека даних забезпечується політиками RLS у базі.

## Етап 2: учні, анкети, підтвердження

- **Студенти** (`#/students`) — таблиця з пошуком (ПІБ, телефон у будь-якому форматі, кімната), фільтрами (клас, поверх, кімната, статус, «Нерозподілені»), сортуванням за клацанням по заголовку, експортом у CSV (роздільник `;`, UTF-8 з BOM, без медичних даних). Телефони — посилання `tel:` для швидкого дзвінка. На телефоні таблиця перетворюється на картки.
- **Картка учня** (`#/students/:id`) — контакти (учень, мама, тато, опікун), чинна анкета, поточна кімната, історія кімнат (лише перегляд), медичний блок (**прихований від `staff_readonly`**; показує, хто вніс і хто змінив), історія версій анкети зі значками «застаріла»/«відхилена» та авторством затвердження.
- **Додати / редагувати учня** (`#/students/new`, `#/students/:id/edit`; admin і educator) — ПІБ, дата народження, клас 9–11, статус (активний / випускник / вибув). Новий учень — нерозподілений. При переведенні з активного у «випускник»/«вибув» учня виселяють із кімнати (`unassign_student`, історія зберігається).
- **«Оновити дані»** на картці — `create_update_request`, посилання виду `<адреса сайту>/#/form/<токен>` (адреса береться з поточної сторінки автоматично, тож при переїзді на інший домен посилання змінюються самі; за потреби — змінна `VITE_PUBLIC_SITE_URL`) з кнопкою «Копіювати» та терміном дії; список активних посилань і «Скасувати». Сирий токен показується **один раз** (в базі лише SHA-256 хеш), тому для вже створених посилань повторно побачити адресу не можна — створіть нове.
- **Публічна анкета** (`#/form/:token`, без входу) — двокрокова: заповнення → **екран перевірки** (усі відповіді за розділами, ПІБ і дата народження виділені, олівець біля розділу повертає до його редагування, кнопка «Назад» у браузері повертає до форми) → «Надіслати анкету». **Згода на обробку персональних даних — на екрані перевірки.** коротка дружня форма для учня з валідацією (телефони `+380XXXXXXXXX`; **усі поля обов'язкові**, крім номера кімнати (лише для інформації), опікуна та медичних відповідей; якщо когось із батьків немає — у ПІБ пишуть «немає» (телефон порожній), якщо немає обох — потрібен опікун; медичні відповіді (алергії, хронічні хвороби) **необов'язкові** — діти можуть їх не знати, вихователь уточнить пізніше; згода на обробку персональних даних). Недійсне, прострочене, відкликане або вже використане посилання виглядає однаково.
- **Збір анкет** (`#/collect`; admin і educator) — **одне спільне посилання на поверх** (4 поверхи — 4 посилання): його надсилають у чат поверху, і кожен учень сам заповнює свою анкету (форма порожня — нічого з бази не підставляється). Посилання діє обмежений час (3–30 днів), нове посилання поверху автоматично скасовує попереднє, є кнопка «Скасувати»; у кожного посилання є ліміт подань. Після відправки анкета зіставляється з учнем у базі **лише за ПІБ + датою народження** (без урахування регістру, пробілів і апострофів): якщо збіг точний і єдиний (активний учень) — анкета прикріплюється до нього автоматично як версія «очікує підтвердження»; інакше потрапляє в чергу **«Не зіставлені»** (значок у меню), де вихователь вибирає учня зі «Схожих», шукає в базі, створює нового учня (обирає клас 9–11) або відхиляє подання як сміття. Журнал **«Хто заповнив»** показує, хто, коли, через яке посилання та як зіставлено; блок **«Хто ще не заповнив»** — за поверхами (нерозподілені окремо). **Підтверджує анкету завжди людина** — на сторінці «Оновлення даних». Персональні посилання «Оновити дані» на картці учня залишено як запасний варіант.
- **Професії:** у публічній анкеті професія обирається **радіокнопками** зі списку (щоб одна професія не писалася по-різному); остання позиція «Інша» відкриває поле для ручного вводу. Список (10 професій з актів, з освітньою базою «на базі 9/11 класів» у назві) веде адміністратор на сторінці «Збір анкет» → «Професії для анкети»: додати, змінити назву, сховати від учнів, видалити; нижче — «Вводили учні, але немає в списку» з кількістю та кнопкою «Додати в список». Збережені анкети не змінюються (зберігається текст обраної назви). Таблиця `professions` (читають активні користувачі, пишe лише admin); перелік до форми віддає Edge Function `get-questionnaire`.
- **Оновлення даних** (`#/updates`; admin і educator) — нові версії анкет, що чекають підтвердження, у порівнянні з чинною (змінені поля підсвічені), кнопки «Підтвердити» / «Відхилити». Якщо учень надіслав анкету повторно, а попередня ще не оброблена, під заголовком показано «Дубль» (повний збіг) або «Повторне подання» з переліком того, що змінилось у новій версії порівняно з попередньою (наприклад, виправлена помилка). У меню біля пункту — червоний лічильник очікуючих версій (оновлюється раз на хвилину та після дій).

Медичні дані, які вніс учень, **не потрапляють у `student_medical`, доки вихователь не підтвердить версію** (до того вони лежать у `student_medical_submissions`; порожнє поле = «без змін»).

**Анкета відповідає паперовому бланку адміністрації:** ПІБ, дата народження, кімната, група, професія, класний керівник і майстер (окремі поля), адреса (область, район, населений пункт, вулиця, будинок, квартира), телефон учня, мама, тато, чим займався у школі / хоче у коледжі та **соціальний статус як чекліст** (сирота, напівсирота, батьки розлучені, дитина з інвалідністю, багатодітна сім'я + кількість дітей, учасники АТО + хто, служба в ЗСУ + хто, статус ВПО, «жодного з переліку»). Структуровані коди зберігаються в `social_status_data` (для майбутніх звітів), а читабельний текст — у `social_status`. Бабуся/дідусь/інша близька людина, яких на папері вписують у рядок мами, вказуються в блоці «Опікун» разом із «ким доводиться» (`guardian_relation`); якщо немає обох батьків — опікун обов'язковий. Медичний блок (алергії, хронічні хвороби) додано понад паперовий бланк.

**Телефон — основний пристрій** (учні 100 %, вихователі ≈75 %): інтерфейс mobile-first — поля 16 px, зони дотику ≥44 px, список учнів стає картками з великими кнопками дзвінка, фільтри згортаються, порівняння версій показується стопкою, кнопки «Підтвердити/Відхилити» закріплені внизу, посилання на анкету можна надіслати через «Поділитися» (Viber/Telegram). Дії, що потребують комп'ютера (переселення перетягуванням, робота з документами), будуть у наступних етапах.

### Edge Functions (публічна анкета)

Анонімний ключ **не читає жодної таблиці**. Учень спілкується лише з двома функціями (`verify_jwt = false`), які всередині користуються `service_role` (ключ ніколи не потрапляє в браузер):

| Функція | Що робить |
| --- | --- |
| `get-questionnaire` | перевіряє токен (хеш, строк, не використаний/не скасований): для персонального посилання повертає ПІБ, дату народження, кімнату та дані з останньої **затвердженої** анкети (без медичних), для спільного — лише `mode: shared` (жодних персональних даних) |
| `submit-questionnaire` | перевіряє payload на сервері (довжини, формати, обов'язкові поля, згода) тими самими правилами, що й браузер, і викликає `submit_questionnaire()` (персональне посилання: «спалює» токен і вставляє `pending`-версію в одній транзакції) або `submit_intake()` (спільне посилання: зіставлення за ПІБ + датою народження або черга «не зіставлені»). Відповідь учню однакова — він не дізнається, чи знайшли його в базі |

Захист: ліміт тіла 20 КБ, ліміт запитів за IP (послаблений — 300 за 10 хв, бо поверх сидить в одній Wi-Fi мережі) і за токеном (таблиця `questionnaire_rate_limits`), а для спільного посилання — ліміт подань на саме посилання (500) і не більше 5 необроблених версій на одного учня (решта йде в «Не зіставлені»), однакова відповідь для будь-якої недійсної причини, помилка перевірки ліміту → «закрито» (503). Код: `supabase/functions/<назва>/index.ts`, спільні модулі — `supabase/functions/_shared/` (`token.ts` — sha256, `questionnaire.ts` — правила валідації, їх імпортує й фронтенд). Деплой: `supabase functions deploy get-questionnaire --no-verify-jwt` і те саме для `submit-questionnaire` (або MCP `deploy_edge_function` з `verify_jwt: false`).

## Користувачі (адміністрування)

Код: `src/features/admin-users/`. Сторінка **«Адміністрування → Користувачі»** (лише `admin`) дозволяє створювати й обслуговувати облікові записи без панелі Supabase. Уся робота з обліковими записами йде через Edge Functions (`admin-list-users`, `admin-create-user`, `admin-update-user`, `admin-reset-password`, `verify_jwt = true`): функція перевіряє JWT, що викликач — **активний admin** (читає `profiles`), і лише тоді користується `service_role` (ключ існує тільки всередині функції). Є обмеження частоти викликів, валідація на сервері, узагальнені помилки; дії пишуться в `audit_log` (`action = 'event'`, без паролів).

### Вхід: вибір вихователя + PIN

Сторінка входу (`#/login`): напис «Гуртожиток», список «Вибір вихователя» (усі активні користувачі з роллю вихователя чи адміна; публічно віддаються лише імена) і одне поле. Рівно **4 цифри** = PIN, усе інше = повний пароль. Нижче є посилання «Вхід за email і паролем» (для облікових записів без PIN, наприклад staff_readonly).

- **Вихователі** входять за PIN. Після **3 невдалих спроб** вхід блокується, доки адміністратор не натисне «Розблокувати» (картка користувача). Лічильник спроб резервується атомарно ще до перевірки, тому паралельний підбір не обходить ліміт. Є також ліміти за IP.
- **Четвертий вихователь (адмін-акаунт)** має два входи в одному полі: PIN → права вихователя (розділ «Адміністрування» закритий, потрібні сервером Edge Functions і RLS відхиляють адмінські дії); повний пароль → права адміністратора. У PIN-сесії є кнопка «Права адміністратора» (повторний вхід паролем). Пароль адміна не блокується помилками з PIN.
- **PIN задає й змінює лише адміністратор** («Задати PIN» / «Змінити PIN» / генерація випадкового, показується один раз). Прості PIN (1111, 1234, 2580…) не приймаються. Хеш PIN (PBKDF2-SHA256, 100 000 ітерацій, сіль) лежить у `pin_credentials`, недоступній із браузера. Створення вихователя: режим «PIN-код» (пароль в Supabase при цьому випадковий і нікому не відомий).
- Технічно: Edge Function `auth-login` (`verify_jwt = false`) перевіряє PIN/пароль і видає сесію (для PIN — через серверний обмін magic-link, лист не надсилається); сесії, видані за PIN, записуються в `pin_sessions`. `private.is_admin()`/`current_app_role()` у БД для таких сесій повертають права вихователя.
- Ризик: список імен публічний, тож хтось може навмисне заблокувати PIN вихователів трьома помилками. Адмін входить паролем (його не заблокувати PIN-ом) і розблоковує.

**Як створити вихователя.** «Додати користувача» → ПІБ, email, роль, поверх (довідково, на доступ не впливає), статус → спосіб передачі доступу:
- **PIN-код** (для вихователів): вкажіть 4 цифри або залиште порожнім (згенерується); PIN показується один раз.
- **Тимчасовий пароль** (для адміністратора): після «Створити» пароль показується **один раз** із кнопкою «Копіювати». Передайте його вихователю; при першому вході застосунок змусить задати власний пароль (мінімум 10 символів) — до цього доступу до розділів немає.
- **Запрошення на email**: Supabase надсилає лист. Вбудована пошта Supabase має суворі ліміти і може бути недоступна — тоді застосунок покаже відповідне повідомлення; створіть користувача з тимчасовим паролем.

**Як скинути пароль.** У картці користувача «Скинути пароль» → підтвердити → новий тимчасовий пароль (показується один раз), старий пароль і всі сесії скасовуються, при наступному вході потрібна зміна пароля.

**Що робити, якщо лист-запрошення не приходить.** Перевірте «Спам»; зачекайте (ліміт листів Supabase — кілька на годину); потім створіть користувача з тимчасовим паролем або натисніть «Скинути пароль» для вже створеного (запрошеного) облікового запису. Постійне рішення — власний SMTP у Supabase (Authentication → SMTP).

**Інше.** «Деактивувати» не видаляє обліковий запис (історія й журнали на нього посилаються): користувач одразу втрачає доступ, сесії завершуються. «Вийти з усіх пристроїв» відкликає сесії без зміни пароля (токен доступу діє до ~1 год, але RLS перестає пускати деактивованого користувача негайно). Захисні правила: адмін не може понизити/деактивувати себе; не можна залишити систему без активного адміністратора (також тригер `profiles_keep_admin` у БД); email унікальний. Кожен користувач змінює свій пароль у меню **«Пароль»** (`#/password`). Примусова зміна — прапорець `profiles.must_change_password`, який знімає RPC `complete_password_change()` (перевіряється інтерфейсом; на рівні RLS доступ до даних він не блокує).

## Структура

```
src/
  lib/supabase.ts      клієнт Supabase
  auth/                AuthProvider, useAuth, RequireAuth, RequireRole, ролі
  routes/              маршрути (AppRoutes) та пункти навігації з фільтром за роллю
  components/          Layout (адаптивна оболонка), службові повідомлення
  lib/                 чиста логіка (diff, CSV, фільтри списку, посилання), запити до БД
  pages/               студенти, картка, редагування, підтвердження, вхід, публічна анкета; решта — заглушки
supabase/              міграції, Edge Functions, SQL-тести
.github/workflows/     деплой на GitHub Pages
```

Маршрути (HashRouter, URL виду `.../dormitory-app/#/students`):

- `#/login` — вхід за email і паролем
- `#/form/:token` — публічна анкета учня (без входу і навігації)
- `#/`, `#/students`, `#/students/new`, `#/students/:id`, `#/students/:id/edit`, `#/updates` (admin, educator), `#/rooms`, `#/documents`, `#/events`, `#/calendar` — після входу
- `#/admin` — лише для `admin`

## Кімнати (етап 3)

Код — у `src/features/rooms/`. Сторінка `#/rooms`:

- схема поверхів 2–5 (на телефоні — вкладки), картки кімнат із заповненістю (`4/5`, зелений = є місця, червоний = заповнена, сірий = неактивна) та учнями;
- блок **«Нерозподілені»** (`v_unplaced_students`);
- перетягування учня мишею/тачпадом (власна реалізація на pointer-подіях, без бібліотек; `Esc` скасовує) між кімнатами/поверхами та з/у пул; перед виконанням — діалог «Підтвердити переміщення?» з необов’язковою причиною. Викликаються `move_student` / `assign_student` / `unassign_student`. Повна або неактивна кімната блокує скидання; відмову сервера (гонка двох вихователів) показано повідомленням, інтерфейс повертається до стану сервера;
- кнопка **«Перемістити»** (вибір кімнати зі списку) — для телефонів і клавіатури; на телефонах перетягування вимкнено (щоб не заважати прокрутці) — лише кнопка;
- місткість: на кожній картці випадаючий список «Місць» (4, 5, 6 або поточне значення; менше за кількість мешканців — недоступно) для вихователя й адміна; ⚙ (лише адмін) — активність кімнати та додавання нових кімнат (так налаштовано `rooms_guard` у БД);
- історія (🕘) учня та кімнати — для всіх активних користувачів; «звідки» пишеться явно (`room_assignments.from_room_id`, міграція `room_assignments_from_room`), а для нерозподіленого учня в пулі показано «було: <остання кімната>»; `staff_readonly` лише переглядає;
- оновлення: Realtime на `rooms`/`room_assignments` (міграція `realtime_rooms_assignments`), а також опитування кожні 15 с і оновлення при поверненні на вкладку.

Тести: `npm test` (чиста логіка у `logic.test.ts`); SQL-тести переміщень проти БД — `src/features/rooms/db-tests/rooms_moves.sql` (виконати одним запитом, усе в транзакції з `ROLLBACK`).

## Документи (етап 5)

Код: `src/features/documents/`. Розділ `#/documents` має три вкладки:

- **Архів** — пошук за назвою, фільтри (категорія, тема, навчальний рік, автор, теги, тип файлу), сортування. Вихователь/адмін завантажує `.docx`/`.pdf` (до 25 МБ; автор — поточний користувач) у приватний бакет `documents`. Завантаження — за підписаним посиланням (60 с). Видаляє адмін або вихователь-автор (як у політиках БД). Файли в Storage мають ASCII-імена (`documents/<uuid>.docx`), справжня назва зберігається в таблиці.
- **Створити на основі…** — обираєте категорію/тему → бачите попередні документи (бейджі року й автора, найновіші першими) → **перегляд** без завантаження → «Створити на основі цього»: файл копіюється в Storage, створюється новий запис (`based_on_document_id`, поточний навчальний рік, ви як автор, назву можна змінити). На картці документа показано «Створено на основі…».
- **Шаблони й автозаповнення** — вибір шаблону, учнів (пошук, уся кімната, увесь поверх) → готовий `.docx` у браузері (docxtemplater + pizzip), з переглядом перед збереженням. Медичні дані в шаблони не підставляються.

Перегляд: `.docx` — бібліотека `docx-preview` (завантажується ліниво), PDF — власний переглядач браузера (iframe). Якщо не вдалося відобразити — показується повідомлення та кнопка «Завантажити».

**Права на шаблони.** Шаблони завжди редагує адмін; вихователь — лише коли в «Адміністрування → Документи» ввімкнено перемикач (`app_settings.educators_can_edit_templates`). Інтерфейс ховає кнопки, а доступ насправді обмежує RLS.

### Поля шаблону `.docx`

Синтаксис — подвійні фігурні дужки; Word може розбивати текст на частини — це нормально. Невідоме або порожнє поле стає порожнім рядком.

| Поле | Значення |
|---|---|
| `{{date}}` | сьогодні, дд.мм.рррр |
| `{{year}}` | поточний навчальний рік |
| `{{educator.full_name}}` | ПІБ того, хто формує документ |
| `{{room}}`, `{{floor}}` | кімната / поверх, якщо вони спільні для всіх вибраних учнів, інакше порожньо |
| `{{count}}` | кількість вибраних учнів |
| `{{student.<поле>}}` | перший вибраний учень (документ на одного учня) |
| `{{#students}} … {{/students}}` | цикл по всіх вибраних учнях; усередині — `{{full_name}}`, `{{index}}` тощо |

Поля учня: `full_name`, `short_name` (Прізвище І.П.), `last_name`, `first_name`, `patronymic`, `birth_date`, `grade`, `group_number`, `profession`, `room`, `floor`, `phone`, `address`, `mother_name`, `mother_phone`, `father_name`, `father_phone`, `guardian_name`, `guardian_phone`, `class_teacher`, `master`; у циклі ще `index` (1, 2, 3…). Дані анкети беруться із затвердженої версії.

**Таблиця зі списком учнів:** у рядку-зразку першу клітинку почніть з `{{#students}}`, а останню завершіть `{{/students}}` — рядок повториться для кожного учня:

| № | ПІБ |
|---|---|
| `{{#students}}{{index}}` | `{{full_name}}{{/students}}` |

### Старі формати (.doc, .rtf, .odt) перед імпортом

Архів приймає лише `.docx` і `.pdf` (старі формати не можна переглянути в браузері). Для імпорту історичних документів є скрипт, що автоматично конвертує старі файли в `.docx` (потрібен LibreOffice, команда `soffice`):

```bash
node scripts/convert-legacy-docs.mjs <папка-з-документами> <папка-результату>
```

`.docx` і `.pdf` копіюються без змін, невдалі файли виводяться в кінці (код виходу 1). Потім імпортуйте вміст `<папка-результату>`. Не комітьте реальні документи в репозиторій. Якщо вихователь спробує завантажити `.doc` у самому застосунку, він побачить підказку, як зберегти файл у Word як `.docx` (конвертація в браузері неможлива).

Довідка по полях шаблону («Як підготувати шаблон», з кнопками «Копіювати») доступна в застосунку у вкладці «Шаблони й автозаповнення» тим, хто може редагувати шаблони.

Перевірки БД для цього етапу: `supabase/tests/003_documents_stage5.sql` (виконується в `BEGIN … ROLLBACK`).
